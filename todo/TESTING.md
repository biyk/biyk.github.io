# План тестирования todo-проекта

Проект работает и выполняет необходимые задачи. План составлен, чтобы не потерять функционал, не затереть и не сломать данные при внесении правок.

## Принципы

- Одна группа правок → прогон регресса → следующий шаг.
- Никаких записей в боевую Google-таблицу из тестов: тесты работают только с временной копией.
- После правок — прогон браузерных тестов и ручной регресс.

# Браузерные тесты (кнопка «Тесты»)

Запуск: кнопка «Тесты» на вкладке «Настройки» (раннер `src/utils/tests/index.js`, автоподхват `*.test.js`). Порядок прогона = алфавитный порядок имён файлов → имена имеют числовые префиксы.

Поток прогона:
1. Создаётся копия боевой таблицы (`gapi.client.drive.files.copy`, ID из настройки `spreadsheetId`) → общий `testId`.
2. Все кейсы гоняются против `testId` (боевая таблица не читается и не пишется).
3. В `finally` копия удаляется (и при ошибке); если удаление не сработало — в консоль логируется ID для ручной уборки.
4. Результаты стримятся в UI по мере выполнения («Выполняется…»), дубль в консоль.

Контекст теста (`run(ctx)`): `ctx.$store`, `ctx.$el` (Vue-прокси, доступны через прототип), `ctx.testId` (ID общей копии), `ctx.setTestId(id)` (устанавливается тестом создания копии).

# Node-тесты (vitest)

Запуск из консоли/CI: `npm test` (в `todo/src`). Цель — зафиксировать текущий функционал и ловить деградацию кода без браузера (быстро, до браузерного прогона).

- Раннер: `vitest run`, конфиг `src/vitest.config.js` — include только `utils/tests/unit/**`, браузерный раннер (glob `./*.test.js`) эти файлы не подхватывает.
- Среда: чистый Node, без jsdom. Браузерные глобалы (`gapi`, `window`, `localStorage`, `sessionStorage`) — стабы в `unit/_globals.js`.
- Структура: `src/utils/tests/unit/*.test.js` — чистая логика без сети (ORM, formatData, getFreeSlots, taskSort/taskDate).
- Известные баги (todo.md, «Устойчивость к сбоям») оформлены как `it.todo(...)` со ссылкой на пункт — прогон остаётся зелёным; при починке `todo` превращается в полноценный тест.
- Планируется дальше: mock-gapi сьюты 04.15–04.18, outbox 08.x — тоже в `unit/`.

| Файл | Покрытие |

# UI-сценарии — план (функциональное тестирование)

## Проблема

Существующие тесты (01–06) проверяют только API-слой — запись/чтение листов через `Table`. **Функциональность не проверяется**: кнопки, пауза, выполнение, удаление, магазин, подсчёты денег/времени/исполнений — всё это не тестируется. Смысл браузерного прогона — именно проверять реальное поведение пользователя.

## Подход

В-страничные UI-сценарии в том же раннере «Тесты», без новой инфраструктуры:

1. Использовать общую копию (`ctx.testId`) — сценарии идут между 04.x и 06 (очисткой), нумерация `05.x`.
2. Временно переключить настройки на копию: `store.commit('settings/NEW_SETTINGS', newArr)` (пишет и в `localStorage['todo-settings']`), затем `todos/initTodos`.
3. Кликать реальные DOM-кнопки (`document.querySelector`) с классами `.start` (▶️), `.pause` (⏸), `.done` (✅/⏹), `.delete` (ⓧ), `.todo-input` + «+» в «Добавить». Переход по вкладкам — через `location.hash` (`#/calendar`, `#/new`, `#/shop`, `#/settings`), ждать монтирования компонента.
4. Ждать завершения асинхронных операций через polling-`waitFor` (учесть `setTimeout` 300/600 мс в `toggleTodo`/`pauseTask`, throttle 1000 мс в `deleteTodo`).
5. Проверять и DOM (строка появилась/исчезла, счётчики), и листы копии (`real_life_tasks`, `task_executions`, `real_life_hero`, `rewards_history`).
6. В `finally` — восстановить исходные настройки (`NEW_SETTINGS` + `todos/initTodos` + `hero/initHero` + `listEvents`), чтобы приложение вернулось в нормальное состояние.

Сценариям нужны уникальные имена задач (таймстамп-суффикс) и проверки по конкретным строкам, а не по глобальным счётчикам (копия к моменту прогона уже содержит данные от 04.x).

# Недостающие тесты — устойчивость (план)

Сейчас (01–06) покрыт только happy-path CRUD на копии. **Не покрыто**: обрыв запросов, сетевая ошибка/пропажа интернета в процессе операции, некорректные данные из API, битый localStorage. Это самые опасные сценарии — именно они «всё потом ломают» (пустой список стирает состояние, дубли строк, необработанные rejection'ы агента).

## Подход к таким тестам

- **Моk вместо реальной сети**: в тесте подменить `gapi.client.sheets.spreadsheets.values.get`, `gapi.client.calendar.events.list` и т.д. на функцию, которая один раз (или всегда) реджектит — затем восстановить оригинал в `finally`. Оффлайн-сценарии без моk не воспроизвести детерминированно.
- Часть тестов — **чистые функции без сети** (`formatData`, `ORM.getFormated`, `getFreeSlots`) — их можно гонять без gapi (`requiresGapi: false`).
- Эти тесты **документируют баги**: до правок (см. todo.md, «Устойчивость к сбоям») — красные, после — зелёные. Писать вместе с правками.

## Политика безопасности данных

- Read-only тесты — только против копии таблицы, боевая таблица не читается и не пишется тестами.
- Запись-тесты (add/update/delete) — только против копии, после прогона копия удаляется.
- Calendar: существующие тесты — только read-only. Планируемые UI-сценарии (пишут в календарь через `toggleTodo`/`deleteTodo`) будут гоняться в тест-режиме (`setCalendarTestMode`) — без реальных событий в календаре.
